## PASS — F1 종결 (측정 방식까지 확인)

과제가 요구한 "탭별 실측 간격 방식"이 **실제로 그렇게 동작하는지**를, 화면의 도움
없이 `data/meta_tree.json` 에서 행별 최소 열 간격을 독립 재계산해 대조했다
(`_min_sep_from_data`).

```
데이터 실측 min column sep:  shared 0.44 · taoist 0.35 · warrior 0.44 · archer 0.44
화면 _tab_min_column_sep():  shared 0.44 · taoist 0.35 · warrior 0.44 · archer 0.44
캡션 폭 (540x960):           shared 143.7 · taoist 121.0 · warrior 143.7 · archer 143.7
```

우치 탭만 121.0px 로 좁아진다 — 상수 0.44 가 아니라 그 탭의 실측 0.35 를 쓴다는
증거다. 새 데이터가 더 좁은 행을 넣어도 규칙이 따라간다.

**우치 row 2** (`talisman_zeal` / `seal_ease` / `spirit_arrows`): 세 캡션이 모두
존재하고, 3쌍 조합 전부 겹침 0, 각 캡션의 실측 글리프 폭이 배정된 열 폭 안에
들어간다 — 486x864 · 540x960 · 960x540 × ko/en 전부.

**이전 리포트가 지목한 전 쌍 재측정** (`luck/revive`, `stone_pillar/bulwark`,
`grip_iron/war_cry`, `moon_step/keen_eye`, `seal_ease/talisman_zeal`,
`seal_ease/spirit_arrows`, `talisman_zeal/spirit_arrows`) — 전부 **측정 가능
(둘 다 렌더됨) 이면서 겹침 0**. "쌍이 사라져서 통과"가 아님을 별도 행으로 확인한다.

탭 전수 조합 겹침도 4탭 × 2언어 × 3해상도 = 24회 전부 0. 캔버스 이탈도 0.

```

```

- **재현 범위**: 960x540 · **en** · `full_defeat` 한 케이스. 같은 해상도의
  `ko full_defeat`, `en/ko typical_defeat`, `control_defeat`, `full_victory` 는 전부 0.
- **교차 검증**: 이전 게이트의 독립 하네스 `tools/qa_n11_3bv.gd` 를 960x540 으로
  돌리면 **동일한 수치**(content 300.0 / box 294.0 / 6.0px)가 나온다. 새 하네스의
  측정 방식 탓이 아니다.
- **화면 증상**: `en_full_defeat_960x540.png` — 종이 오른쪽에 **스크롤바가 그려진다**
  (오너의 무스크롤 규칙 위반). 글리프가 잘리지는 않는다 — 4배 확대 확인 결과
  `4 achievements — see the list` 는 온전히 렌더된다.
  `materials +128 · pages +17` 둘째 줄이 스크롤바 밑으로 붙는다.
- **심각도**: BLOCK → **MEDIUM**. 이전 156px 에서 6px 로 줄었고 글자 손실은 없다.
  다만 오너 규칙상 스크롤바가 보이면 안 된다.

### 원인 — 여백 기부 분기가 이 경로에서 죽어 있다

`scripts/ui/result_screen.gd:135-155`:

```gdscript
_row_scroll.custom_minimum_size = Vector2(0.0, minf(content, room))   # 여기서 이미 room 으로 잘린다
var wanted: float = chrome + _row_scroll.custom_minimum_size.y        # 그래서 wanted == available
if wanted > available:                                               # 절대 참이 되지 않는다
    var give: float = minf(wanted - available, (margin_y - PANEL_MARGIN_Y_MIN) * 2.0)
```

측정된 수치로 확인:

```
available = 540 - 24*2                     = 492
chrome    = style_y 22 + header 48 + CTA 64 + BODY_MARGIN 48 + SPACE_MD 16 = 198
room      = 492 - 198                      = 294
content                                    = 300      → 6px 초과
custom_min = min(300, 294)                 = 294      (여기서 잘린다)
wanted     = 198 + 294                     = 492 == available   → 기부 분기 미실행
```

`content` 가 `room` 을 넘는 **바로 그 경우에만** 여백 기부가 필요한데, `wanted` 를
이미 잘린 값으로 계산하기 때문에 정확히 그 경우에 조건이 거짓이 된다.
`PANEL_MARGIN_Y_MIN := 8.0` 이 열어 둔 **32px** (=(24-8)×2) 가 통째로 미사용이다.
6px 만 쓰면 되므로 **현재 상수 안에서 해결 가능**하다.

**권고 (게임 코드 담당자 몫 — 이번 세션은 수정 금지)**: `wanted` 를 자르기 전 값으로
계산한다.

```gdscript
var wanted: float = chrome + content        # chrome + minf(content, room) 이 아니라
if wanted > available:
    # ...기부...
    _row_scroll.custom_minimum_size = Vector2(0.0, minf(content, room))
```

기부가 실행되면 `available 524 → room 326 >= content 300` 이 되어 스크롤이 사라진다.
