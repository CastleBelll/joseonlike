### 1a. 선이 캡션 글자를 관통한다 — 가장 눈에 띄는 문제

캡션은 노드 바로 **아래** 중앙에 놓이고, 부모→자식 가지는 노드에서 **아래로** 나간다.
그래서 모든 세로 가지가 자기 캡션 글자 사이를 지나간다. 캡션 Label이 나중에 그려져
글자는 살지만, 선은 글자 사이에서 끊어져 보인다.

- 증거: `zoom_trunk_caption_line.png` — "철골"의 철/골 사이, "2/3 · 240냥"의 · 와 240 사이를 금색 선이 관통
- 증거: `zoom_taoist_trunk_caption.png` — "봉인 간파" 와 "잠김 · 750냥" 을 잠김 가지 두 줄이 관통
- 증거: `m_540x960_en_warrior_top.png` — `hwando_hone→grip_iron` (3행 건너뛰기) 한 줄이
  "Blade Honing / Locked · 440 / coins" → Mountain Stance → "Pillar Stance / Locked · 250 / coins"
  → Pillar Stance 디스크까지 세로로 관통. 열 전체를 칼로 그은 모양이다.

N11-9의 F11에서 **줄기(trunk)** 는 캡션마다 끊어 이 문제를 이미 해결했다.
N11-11이 새로 넣은 **가지(branch)** 는 그 처리를 물려받지 않았다 — 같은 버그의 재도입이다.

### 1b. 줄기가 점선이 됐다

캡션이 줄기 x를 스치기만 해도 줄기를 끊는데, 공용탭 캡션은 폭이 넓어 34행 전부가 줄기를

```

  없음46 · 줄기13 · 가지9 · 줄기69 · 없음83 · 가지9 · 줄기69 · 없음71 · 줄기94 · 없음71 · 줄기98
  → 줄기 가시 55~58%, 69~98px 조각과 71~83px 공백이 거의 1:1로 번갈아 나옴
비교) 우치탭 (줄기를 끊는 캡션이 1개뿐)
```

즉 공용탭에서 줄기는 나무가 아니라 **파선(dash)** 이다. 가지가 뻗어 나갈 몸통이 없으니

참고: 하네스가 "root stub이 줄기 공백 안에서 시작한다"고 17건 표시했지만, 픽셀 확인 결과
가지의 합류점(wishbone 꼭짓점)이 줄기 조각의 끝단과 거의 맞물려 **육안으로는 떠 보이지 않는다**.
이 항목은 결함으로 올리지 않는다.

### 1c. 긴 가지가 중간 노드를 관통

## 2. 상태색 가독 — FAIL

실측 대비(WCAG, 배경 `NIGHT_BROWN #241a12`):

| 요소 | 색 | 배경 대비 |
|---|---|---|
| 구매 완료 가지·링 `GOLD_BORDER` | `#c49a3d` | 6.53:1 |
| 구매 가능 가지 `WOOD` | `#e2a057` | 7.63:1 |
| 잠김 가지 `CARD_BORDER_DIM` | `#453d54` | **1.66:1** |
| 브리딩 링 `GOLD@0.65` (합성 `#b29636`) | — | 5.93:1 |
| 줄기 `WOOD_BORDER` | `#6e4322` | **2.02:1** |

**상태끼리의 분리도가 문제다:**

| 쌍 | 대비 |
|---|---|
| 구매 완료 vs 구매 가능 | **1.17:1** |
| 구매 완료 vs 선택됨 | 1.90:1 |
| 구매 완료 vs 잠김 | 3.92:1 |
| 구매 가능 vs 잠김 | 4.59:1 |
| 노드 칠 `CARD_BG_SELECTED` vs `CARD_BG` | **1.06:1** |

3px 선에서 1.17:1은 구분 불가다. 스크린샷에서도 철골(2/3 보유)과 빠른 걸인(구매 가능)의
테두리·칠을 색만으로 가려낼 수 없다. 실제 구분은 캡션 문구(`2/3 · 240냥` vs `구매 가능 · 150냥`)가
전부 하고 있고, 이건 N10-20이 설계한 대로다 — 다만 N11-11 커밋이 "colour speaks the node's
state"라고 주장한 부분은 **성립하지 않는다**.

추가로 상태 언어에 구멍이 하나 있다:

> 정지 링(steady gold ring)은 `rank >= max_rank` 일 때만 그려진다.
> 일반 프로필(4000냥, 일부 구매)에서 공용탭 34노드 중 **정지 링을 단 노드는 0개**,
> 브리딩 링은 22개였다. 즉 "이미 내 것"이라는 시각 언어가 화면에 존재하지 않는다.
> 2/3 보유한 노드는 여전히 살 수 있으므로 **한 번도 안 산 노드와 똑같이 숨쉰다.**

잠김 가지(1.66:1)는 사실상 안 보이는데, 이건 의도(dim)로 볼 수도 있다. 다만 비텍스트 요소
최소 3:1에는 못 미치므로 "잠긴 경로가 어디로 이어지는지"는 읽히지 않는다.

## 4. 호버 / 클릭 — PARTIAL FAIL

마우스 이벤트 주입으로 스케일을 프레임 단위 실측했다.

**호버 인** (`HOVER_TWEEN_SEC 0.1`, EASE_OUT):
```
1.017 1.033 1.050 1.066 1.083 1.100 1.100 1.100 ...   (6프레임 = 0.1s, 사운드 ui_click)
```

**프레스** (punch 0.92 → 1.0):
```
1.100 0.968 0.929 0.948 0.960 0.974 0.987 1.000 1.000 ...  (8프레임 ≈ 0.13s, 사운드 ui_open)
```

잘려나가는 건 없다. 호버 확대 시 디스크가 캡션 상단을 3.6px 침범하지만 캡션 leading 안이라
글자 잘림 없음. 행 이웃 중심거리 149.7px vs 확대 지름 79.2px — 이웃과 충돌 없음.

### 4a. 클릭이 호버 상태를 파괴한다 (버그)

`_on_node_pressed`의 punch 트윈이 무조건 `Vector2.ONE`으로 끝난다. 포인터가 아직 노드 위에
있는데도 디스크가 **1.00으로 줄어 앉는다**(실측 20프레임 후 1.000). 클릭한 순간 "지금 이걸
가리키고 있다"는 표시가 사라진다. 호버 트윈도 이전 트윈을 `kill()`하지 않아 빠르게 들락거리면
두 트윈이 같은 속성을 다툰다.

### 4b. 호버 사운드가 난사된다

`mouse_entered`가 `ui_click`(min_interval 0.05s = 초당 최대 20회)을 재생한다.

- 포인터로 공용탭 34노드를 훑는 동안 `ui_click`이 계속 발화.
- 더 나쁜 건 **휠 스크롤**이다. 포인터를 고정한 채 휠 30스텝을 굴리면 콘텐츠가 포인터 밑을
  지나가며 `mouse_entered`가 **12회** 발화 → `ui_click` 12번. 스크롤만 했는데 딸깍거린다.
  (실측: `WHEEL scroll 0 -> 2396, mouse_entered fired 12 times during 30 wheel steps`)
- `ui_open`(프레스)/`ui_click`(호버)의 의미도 뒤집혀 있다. 보통 클릭이 `ui_click`이다.

터치 경로는 깨끗했다: 탭 1회 = `ui_open` 1회, 손가락을 뗀 뒤 60프레임 후 스케일 1.00
(잔류 확대 없음). `emulate_mouse_from_touch=true`지만 문제를 만들지 않았다.

## 6. 성능 — PASS (경고)

`_process`가 매 프레임 `_canvas.queue_redraw()`를 호출한다. 같은 씬에서 `set_process(true/false)`
A/B로 재드로 비용만 분리했다 (vsync off, `max_fps 0`, Intel UHD 770).

| 탭 | 재드로 ON | 재드로 OFF | 재드로 비용 |
|---|---|---|---|
| 공용 (34노드) | 103 fps = **9.71 ms/frame** | 1050 fps = 0.95 ms | **+8.76 ms** |
| 우치 (15노드) | 233 fps = 4.29 ms | 1069 fps = 0.94 ms | +3.35 ms |
| 석주 (10노드) | 419 fps = 2.39 ms | 1036 fps = 0.97 ms | +1.42 ms |

**vsync 켜고 공용탭: 60.0 fps 지속 — 55+ 기준 통과.**

(`Performance.TIME_PROCESS`는 이 빌드에서 프레임당 값으로 신뢰할 수 없는 수치를 냈다 —
warrior 탭에서 redraw OFF가 ON보다 크게 나옴. 위 표는 전부 **벽시계 프레임 시간**으로 계산했다.)

다만 데스크톱에서조차 정지 화면 하나가 16.6ms 예산의 **53%**를 쓴다. 원인은 그리기가 아니라
매 프레임 반복되는 조회다:

- `_draw_graph`가 노드마다 `_is_buyable()`을 **2회**(가지 색 + 링) 호출
- `_is_buyable` → `MetaTree.can_purchase` → `MetaTree.node()`가 **69노드 선형 스캔**,
  `is_unlocked`가 한 번 더 스캔 → 호출당 최대 138회 문자열 비교
- 공용탭 34노드 × 2 = 68회/프레임 ≈ 9,400회 비교/프레임
- `_tab_nodes()`(69노드 순회 + 새 Array 할당)도 프레임당 2회 이상
- 여기에 캡션 34개 `get_rect()` + gap 정렬이 매 프레임

실측: 공용탭 `_is_buyable` 1패스 966µs, 프레임당 2패스 = 약 1.93ms — 그것만으로 60fps 예산의
11.6%. 나머지는 폴리라인 35개(각 15점) + 아크 22개(각 32세그먼트) 재구축.

GDScript가 3~5배 느린 중급 폰이면 30~50ms/frame → **20~30fps**가 나올 수 있는 구조다.
숨쉬는 링 하나 때문에 화면 전체를 매 프레임 다시 그릴 이유는 없다.

# 개선사항 — 체감 위주

오너 지시("QA 돌려보고 개선사항 받아서 수정해")에 대한 제안. **구현은 하지 않았다.**
우선순위는 "오너가 화면을 보고 바로 말할 확률" 순.

## P1 — 지금 화면이 지저분해 보이는 이유 3가지

**I-1. 가지를 캡션 옆으로 내보내라 (근본 해결)**
지금 제어점은 `Vector2(from.x, to.y)` — 부모 x에서 **아래로** 출발하므로 반드시 부모 캡션을
관통한다. 제어점을 `Vector2(to.x, from.y)` 로 뒤집으면 곡선이 디스크 **옆구리**에서 먼저
가로로 빠져나간 뒤 내려간다. 캡션 열(노드 중심 ±caption_width/2)을 통과하지 않게 되고,
"가지가 옆으로 뻗는다"는 마인드맵 느낌도 이쪽이 훨씬 강하다. 한 줄 변경으로 캡션 관통
17~33건 대부분이 사라진다.
차선책(더 안전): 줄기가 이미 쓰는 캡션 gap 로직을 `_draw_branch`에도 적용해 폴리라인을
캡션 사각형에서 잘라 그린다.

**I-2. 줄기를 끊지 말고 캡션을 비켜라**
공용탭 줄기 가시율 55~58%(우치탭은 82%)는 몸통이 없다는 뜻이다. 캡션 gap 판정이
`rect ± 4px` 로 **박스 전체**를 보는데, 실제로 줄기와 겹치는 건 가운데 몇 글자뿐이다.
대안 셋 중 하나:
  a) 캡션 폭이 줄기를 겨우 스칠 때는 캡션을 좌우로 6~10px 밀어 아예 안 겹치게 한다 (권장)
  b) 줄기를 끊는 대신 캡션 뒤에 `NIGHT_BROWN` 반투명 판을 깔고 줄기는 통과시킨다
  c) 줄기 폭을 10px → 6px 로 줄이고 gap 판정을 실제 글자 폭 기준으로 좁힌다

**I-3. 구매/구매가능을 색이 아니라 형태로 갈라라**
1.17:1은 어떤 튜닝으로도 안 읽힌다. 색은 그대로 두고 **선 언어**를 추가한다:
  - 구매 완료: `GOLD` `#ffd94a` (12.4:1), 실선 4px
  - 구매 가능: `WOOD` `#e2a057` (7.6:1), 실선 3px
  - 잠김: `CARD_BORDER_DIM`, **파선** 2px
색맹 접근성 원칙(색만으로 정보 전달 금지)도 이걸로 함께 만족한다.
그리고 **정지 링을 `rank >= 1`부터** 달아라. 지금은 만렙에만 붙어서 일반 프로필의 정지 링
개수가 0이다 — "내 것"이라는 언어가 화면에 없다.

## P2 — "퍼져나가는 느낌"이 부족한 지점

**I-4. 공용탭 하단 23개가 사다리다**
`refine_*` 23노드는 전부 `requires: []` 라서 부모 없이 줄기 stub만 달린다. 19개의 똑같은
반쪽 곡선이 세로로 반복되면 마인드맵이 아니라 목록이다. 둘 중 하나:
  a) 데이터에서 refine 노드를 짧은 사슬로 묶는다 (`refine_attack_damage → refine_attack_speed` 등).
     실제 게이팅 의미도 생기고 그림도 나무가 된다.
  b) 코드만으로 하려면 stub의 부착 높이와 곡률을 행마다 흔들어라
     (`_row_height() * (0.35 + 0.2 * (row % 3))`). 반복 패턴만 깨져도 훨씬 유기적으로 보인다.

**I-5. 탭을 열 때 가지가 자라는 연출 (가장 저렴한 체감 개선)**
지금 화면에 들어가면 완성된 그림이 그냥 있다. 마인드맵의 "퍼져나감"은 정지 그림이 아니라
**자라는 순간**에 느껴진다. `_populate_tab` 에서 `_grow: float` 0→1 트윈(0.35s, EASE_OUT)을
돌리고 `_draw_branch`가 `t <= _grow` 구간까지만 폴리라인을 내보내면, 줄기에서 가지가
바깥으로 뻗어나가는 그림이 공짜로 나온다. 행 인덱스로 0.03s씩 stagger를 주면 더 좋다.
(이미 매 프레임 redraw 중이라 추가 비용 0 — 오히려 이게 redraw가 존재할 유일한 이유다.)

**I-6. 구매가 나무를 먹이는 것처럼 보이게**
현재 버스트는 0.5초·3px·링 하나로 얌전하다. 구매의 의미는 "이 노드가 켜졌다"가 아니라
"여기서부터 아래가 열렸다"이므로:
  - 버스트와 동시에 그 노드 → **자식 노드로 향하는 가지를 0.2초 동안 밝게 훑어라**
    (선을 따라 흐르는 하이라이트). 잠겨 있던 자식이 켜지는 게 눈에 보인다.
  - 디스크 자체에 1~2프레임 흰 플래시. 지금은 원 하나만 커져서 "타격감"이 없다.
  - 버스트 획 3px → 4px, 종료 반경 1.3× → 1.6×.

**I-7. 가로모드가 화면 절반을 버린다**
`m_960x540_ko_trunk_top.png`: 960px 폭에서 트리는 좌측 약 420px만 쓰고, 우측 절반은
작은 상세 카드 하나와 빈 밤하늘이다. 그런데도 스크롤은 남아 있다. 가로에서는
행 피치를 더 줄이는 대신 **트리 열 자체를 넓히거나**, 2열 배치를 좌우로 벌려
캡션 폭 여유를 만드는 편이 훨씬 낫다. 지금은 세로 UI를 가로에 끼워 넣은 모양이다.

**I-8. 숨쉬는 노드를 줄여서 "다음 한 걸음"을 가리켜라**
4000냥이면 34개 중 22개가 동시에 숨쉰다. `MetaTree.cheapest_next()`가 이미 "다음 한 방"을
계산해 두었다. 브리딩 링을 **가장 싼 3~5개**로 제한하면 화면이 플레이어에게 방향을
알려주는 물건이 된다. 나머지 구매 가능 노드는 정적 `WOOD` 테두리로 충분하다.
(연출 강도는 지금이 약한 게 아니라 **대상이 너무 많은 것**이 문제다.)

## P3 — 손맛 / 자잘한 버그

**I-9. 호버 사운드를 끄거나 바꿔라**
`mouse_entered` → `ui_click` 은 휠 스크롤만 해도 12회 딸깍인다. 셋 중 하나:
  a) 호버는 무음으로 (스케일만으로 충분)
  b) 구매 가능한 노드에서만 울리게
  c) `min_interval_sec`이 더 긴 전용 id를 쓰고, 클릭에 `ui_click` / 호버에 조용한 소리로 **의미를 바로잡아라**
     (지금은 호버=`ui_click`, 클릭=`ui_open` 으로 뒤집혀 있다)

**I-10. punch가 호버를 죽이지 않게**
`_on_node_pressed`의 트윈 종점을 `Vector2.ONE` 대신
`Vector2.ONE * (HOVER_SCALE if button.is_hovered() else 1.0)` 로. 그리고 호버/프레스 트윈은
노드별로 보관해 새로 만들기 전에 `kill()` — 지금은 빠르게 들락거리면 트윈이 겹친다.

**I-11. 호버 시 링도 같이 커지게**
호버 디스크 반경 39.6px가 링 반경 37.5~42.5px를 사이클의 42% 동안 덮는다.
링 반경에 `button.scale.x`를 곱하거나, `PULSE_RING_PAD`를 4 → 8로 올려라.

**I-12. 탭 전환 시 `_bursts.clear()`**
`_on_tab_pressed` 한 줄. 지금은 다른 탭에서 링이 끝난다.

**I-13. 캡션 고아 줄바꿈**
`구매 가능 · 230` / `냥`, `Locked · 440` / `coins`. 숫자와 단위 사이를 non-breaking space로
묶거나, 상태 줄을 `구매 가능` / `230냥` 두 줄 고정 포맷으로 바꿔라. 영어는 거의 전부 3줄이라
행 간격까지 잡아먹는다.

**I-14. 매 프레임 redraw를 조건부로**
지금 구조는 정지 화면에 데스크톱 8.8ms/frame(60fps 예산의 53%)를 쓴다. 두 단계면 거의 공짜가 된다:
  a) `_is_buyable` 결과를 `_refresh()` 시점에 노드별로 캐시 (프레임당 `can_purchase` 68회 → 0회).
     `MetaTree.node()`가 69노드 선형 스캔이라 이게 비용의 대부분이다.
  b) 재드로를 **필요할 때만**: 버스트가 살아있거나, 숨쉬는 노드가 있고 링 반경이 실제로
     1px 이상 변했을 때만 `queue_redraw()`. 링만 별도 `Control`로 분리하면 더 깨끗하다.
  I-5(자라는 연출)를 넣더라도 그건 0.35초짜리 일회성이므로 상시 redraw 근거가 되지 않는다.
