## 1. 구조 — 무엇이 실제로 그려지는가

`_compute_radial`은 노드를 **깊이(tier) = 링**으로 배치한다고 주석에 적혀 있지만, 링은 캔버스에 들어가는 개수만큼만 생긴다:

```
max_rings = floor((1 - inner) / pitch) + 1
inner     = (HUB_RADIUS + disc + 12) / span      # span = min(rx, ry) = 208
pitch     = (disc + RING_GAP) / span
slot      = min(depth, max_rings)                # 남는 tier는 바깥 링에 합류
```

540×960에서 캔버스는 **492 × 538**, 타원 반지름 `rx = 208`, `ry = 231`. 원판 56px 기준 `inner = 0.5096`, `pitch = 0.3558` → **링은 2개밖에 안 들어간다.**

| 탭 | 상태 | 노출 | 실제 링 수 | 링 fraction | tier가 링에 합류한 방식 |
|---|---|---|---|---|---|
| 공용 | fresh | 5/17 | 1 | `[0.5096]` | tier 1 |
| 공용 | bloom | 17/17 | 2 | `[0.5096, 0.8654]` | **링2 = tier 2+3 (12노드)** |
| 연마 | fresh | 5/27 | 1 | `[0.5096]` | tier 1 |
| 연마 | bloom | 27/27 | 3 | `[0.4349, 0.7160, 0.9970]` | **링3 = tier 3+4+5 (17노드)** |
| 우치 | fresh | 4/15 | 1 | `[0.5096]` | tier 1 |
| 우치 | bloom | 15/15 | 2 | `[0.5096, 0.8654]` | **링2 = tier 2+3+4+5 (11노드)** |

## 8. 신규 — 레이아웃 비결정성 (`_node_scale` 이월)

`_compute_radial`은 `inner`/`pitch`를 `_node_size()`로 계산한 **뒤에** `_node_scale = 1.0`으로 리셋하고 축소 루프를 돈다. 즉 **이번 배치가 지난 배치의 원판 크기를 입력으로 쓴다.**

```gdscript
var inner: float = (HUB_RADIUS + _node_size() + 12.0) / span   # ← 이전 호출의 _node_scale
var pitch: float = (_node_size() + RING_GAP) / span            # ← 같음
...
_node_scale = 1.0                                              # ← 여기서야 리셋
for _attempt: int in 3:
    if _min_separation() >= _node_size() + 4.0: break
    _node_scale *= 0.85
```

`_refresh()`가 매번 `_layout_nodes()`를 부르므로(선택 탭, 구매, 캔버스 resize 전부) 축소가 **누적**된다.

측정 (연마 bloom, 같은 탭·같은 데이터, 진입 스케일만 다르게):

| 진입 `_node_scale` | 정착 `_node_scale` | 기존 노드 이동 |
|---|---|---|
| 1.00 | 0.722 | 기준 |
| 0.85 | 0.722 | **mean 16.1px, sd 3.50, min 8.5, max 18.7** |

정상 흐름에서도 이미 불일치가 남는다: 연마 bloom의 링 fraction `0.4349`는 **40.5px 원판**(= 56 × 0.85²) 기준인데, 실제로 그려진 원판은 **47.6px**(= 56 × 0.85)이다. **링 간격이 원판보다 7px 작게 잡힌 채 렌더된다** — §2의 −7.1px FAIL이 여기서 나온다.

사용자에게 보이는 형태: 어떤 탭을 거쳐 연마에 들어오느냐에 따라 원판 크기와 노드 위치가 달라진다.
